# 배포 흐름 — 편집에서 실행까지
> 워크스페이스 저장은 곧 커밋이고, 실행은 배포 요청과 관리자 승인을 거친다. 어떤 검사가 언제 도는지.
keywords: 배포, deploy, 요청, request, 승인, approve, 검토, 커밋, commit, 저장, 워크스페이스, 사전 검사, startup check, 빌드, build, 롤백, rollback, 미리보기, preview, 충돌, rebase, 제거, remove, 삭제, 취소, 앱 페이지, 시작, 중지, 로그

## 편집과 저장
- 워크스페이스(`/{부서}/{저장소}/_edits/main`)에서 저장하면 저장소의 `main` 브랜치에 바로 커밋된다. 브랜치나 PR을 부서가 다룰 필요는 없다.
- 저장했다고 앱이 바뀌지는 않는다. 실행 중인 앱은 마지막으로 승인·배포된 버전이다.

## 배포 요청
- `/{부서}/{저장소}/deploy` 에서 제목과 설명을 적고 제출하면, 현재 `main`의 파일이 중앙 배포 저장소에 스냅샷으로 복사되고 관리자에게 승인 요청(PR)이 열린다. 한 앱에 열린 요청은 하나뿐이며 새 요청은 이전 요청을 자동으로 취소한다.
- 폼에서 함께 요청하는 것: 승인이 필요한 패키지, 외부 접근 호스트, 파일 다운로드 허용, 메모리·데이터 한도 상향, 접근 모드. 각 항목에는 이유를 적어야 한다.
- 제출 전 검사:
  - **사전 검사(Pre-deploy check)**: 모든 Python 파일의 문법, import 시점에 실패할 정의되지 않은 이름, `main.py`의 `app` 유무, HTML의 닫히지 않은 태그, JavaScript 문법. 줄 번호와 함께 표시된다.
  - **시작 검사(Startup check)**: 현재 버전을 배포와 똑같이 빌드해 격리된 환경에서 `main`을 import하고 `app`을 확인하고 startup을 끝내고 `/health`에 요청한다. 실패한 버전은 제출할 수 없다. 패키지 승인이 아직 없으면 "Not run yet"으로 표시되고 제출은 가능하다 (승인이 곧 요청 내용이므로).
  - **프리플라이트**: 서버 Python, `main.py` 존재, `requirements.txt` 형식, 버전 조합이 설치 가능한지.
- 요청 페이지에는 변경된 파일, 승인 항목, 서버 용량 판단, AI 검토 의견이 보이고 관리자와 대화할 수 있다.

## 승인 뒤에 일어나는 일
1. 패키지 환경 빌드 (같은 requirements면 캐시 재사용).
2. 데이터 마이그레이션 적용 (옛 앱이 아직 서비스 중).
3. 새 릴리스 시작 → `/health` 확인 (약 30초).
4. 통과하면 심볼릭 링크 교체로 새 버전이 서비스된다. 실패하면 이전 버전이 계속 서비스되고 실패 이유가 앱 페이지와 관리 화면에 남는다.
- 관리자는 승인 전에 요청된 버전을 별도 복사본으로 미리 실행해 볼 수 있다 (미리보기). 실제 앱과 데이터에는 영향이 없다.
- 요청이 오늘의 중앙 저장소와 충돌하면 관리자가 버튼 하나로 최신 기준에 다시 올린다 (rebase).

## 앱 페이지 — /{부서}/{저장소}/_app
- 상태(실행 중/중지/실패), 헬스, 최근 로그, 강제 중지 이유, 사용 중인 메모리·데이터.
- 시작/중지/재시작, 이전 버전으로 롤백, 환경 변수 관리, 접근 모드 변경, 허용된 패키지 목록.
- 앱을 플랫폼에서 내리려면 여기서 "제거 요청"을 낸다. 관리자가 승인하면 앱과 정책이 정리되고, 그 뒤에야 저장소를 삭제할 수 있다. 배포된 적 없는 저장소는 바로 삭제된다.
