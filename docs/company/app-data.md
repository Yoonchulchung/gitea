# 앱 데이터 — SQLite 영속성, 용량, 마이그레이션

**구현 전에 합의하는 계획 문서.** 플랫폼 전체 구조는 [app-platform.md](app-platform.md),
구현 계약은 [app-platform-impl.md](app-platform-impl.md).

## 1. 왜 필요한가

부서 앱이 `sqlite3.connect()`에서 `unable to open database file`로 죽는다. 앱 버그가
아니라 **플랫폼에 영속 데이터 자리가 없어서** 생기는 구조적 실패다.

- 릴리스 트리는 읽기 전용이다 (`company/appsandbox.go:332` — `--ro-bind .../app /app`).
  앱의 cwd가 `/app`이므로 상대 경로 DB는 쓸 수 없는 곳을 가리킨다. SQLite는 WAL·shm
  파일 때문에 파일이 아니라 **디렉터리** 쓰기 권한을 요구하고, 그래서 이 메시지가 난다.
- 쓸 수 있는 곳은 `p.run` 하나뿐인데, 여기는 소켓과 TMPDIR이 사는 폐기 가능한 스크래치다.
- 설령 릴리스 안에 썼더라도 배포마다 디렉터리가 새로 생기고 GC 대상이다. 배포 한 번에
  데이터가 사라진다.

그리고 지금 구조에 DB를 그냥 붙이면 **데이터가 소실되는 경로가 세 개 열린 채로** 시작한다.
아래 2·3절이 그 세 개를 닫는다.

## 2. 데이터 위치 — 이름이 바뀌어도 같은 곳

### 문제

`appKey = sha256(owner + "/" + repo)` (`company/appstate.go:181`). 리포 이름이 바뀌거나
다른 조직으로 옮겨지면 키가 바뀌고 홈이 바뀐다. `company/admin_deploys.go:101`에 이미
"a rename orphans the old app"이라고 적혀 있다. 지금은 재배포로 끝나는 비용이지만,
DB가 생기면 데이터 유실이다.

또 `RemoveApp`은 `os.RemoveAll(p.home)`으로 홈을 통째로 지운다
(`company/app_control.go:136`). 주석의 근거는 "코드는 git에 남는다"인데, **데이터에는
그 논리가 성립하지 않는다.**

### 해결 — 물리 위치는 repo ID, 논리 위치는 고정

데이터만 이름과 무관한 트리로 분리한다. 키는 리포 **ID**(int64)다. ID는 이름 변경에도
조직 이전에도 바뀌지 않으므로, rename 훅이 아예 필요 없다.

```
<AppDataPath>/company-app-data/<repoID>/
  app.db                     # 이 앱의 전부
  app.db-wal, app.db-shm     # WAL일 때 SQLite가 만든다
  .meta.json                 # 마지막으로 본 owner/repo, created_at, removed_at
  .snapshots/<version>-<ts>.db
```

`company-apps/<hash>/`(릴리스·venv·run·logs)는 그대로 둔다. 전부 재생성 가능한
것들이고, `RemoveAll` 대상으로 남아도 안전하다.

### 앱마다 파일 하나 — 자유 쓰기 디렉터리를 주지 않는다

앱 사이의 경계는 **파일 경계**다. 공유 DB도, 공유 스키마도, 테넌트 컬럼도 없다.
그리고 그 디렉터리에는 DB 말고 아무것도 넣지 않는다 — 앱이 마음대로 쓰는 `files/`
같은 것을 두지 않는다. 이유가 셋이다.

1. **스냅샷 정합성.** 전부 DB 안에 있으면 백업 한 번이 앱 전체의 일관된 사본이다.
   파일이 DB 옆에 따로 있으면 백업이 찢어지고, 복원이 "DB는 어제 것, 파일은 오늘 것"이
   된다.
2. **용량 계산.** 상한이 곧 DB 파일 크기라 디렉터리 순회가 거의 필요 없어진다.
3. **공격 표면.** 10절의 심링크 문제가 대부분 사라진다.

**그래도 디렉터리 자체는 필요하다.** SQLite는 WAL·journal 형제 파일을 DB **옆에**
만들고, WAL 모드에서는 마지막 커넥션이 닫힐 때 그것을 **지웠다가 다음에 다시 만든다.**
그래서 디렉터리에 쓰기 권한이 없으면 WAL로는 아예 열리지 않는다. "DB 하나만 들어 있는
최소 디렉터리"가 실현 가능한 가장 좁은 형태다.

업로드 파일이 필요하면 BLOB으로 DB에 넣는다. 부서 앱 규모에서 충분하고, 위 세 가지를
전부 지킨다.

### 대안: 파일 단위 심링크·바인드 — 검토했고, 채택하지 않았다

디렉터리 대신 파일을 하나씩 링크하면 앱이 파일을 **만들 수조차** 없게 된다. 매력적인
방향이라 실제로 재 봤다(SQLite 3.51.2).

| 실험 | 결과 |
|---|---|
| WAL 모드에서 커넥션을 모두 닫음 | `-wal`·`-shm`이 **삭제된다**. 다음 열기에서 다시 만든다 |
| 읽기 전용 디렉터리 + WAL | `attempt to write a readonly database` — 열리지 않는다 |
| 심링크로 DB를 열었을 때 `-wal` 위치 | 심링크가 있는 곳이 아니라 **원본 경로 옆**에 생긴다 |
| 읽기 전용 디렉터리 + `PERSIST`/`TRUNCATE` + 미리 만든 `-journal` | **쓰기 성공** |

심링크는 세 번째 줄에서 끝난다. SQLite가 경로를 정규화해 형제 파일 이름을 만들기 때문에
WAL은 샌드박스 안이 아니라 원본 디렉터리 옆에 생기고, 그 경로는 샌드박스에 마운트되어
있지도 않다. Landlock 모드에는 마운트 네임스페이스가 없어 애초에 해당 사항이 없다.

네 번째 줄은 진짜로 동작한다. `app.db`와 `app.db-journal`을 파일 단위로 바인드하고
rollback journal 모드를 쓰면 읽기 전용 디렉터리에서도 쓰기가 된다. 그런데 채택하지
않는다.

- **`journal_mode`는 앱이 바꿀 수 있는 PRAGMA다.** 어시스턴트가 흔히 쓰는 한 줄
  (`PRAGMA journal_mode=WAL`)이면 그 순간 앱이 깨진다. 밖에서 강제할 방법이 없는 것을
  전제로 삼는 설계는 성립하지 않는다.
- WAL을 **쓸 수 있는 환경에서도** 못 쓰게 된다. 5절의 방향(환경을 재서 최선을 고른다)과
  정면으로 어긋난다.
- 저널 파일의 생명주기를 플랫폼이 떠안게 되는데, SQLite가 한 번이라도 unlink하면
  조용히 깨진다.

얻는 것과 비교하면 남는 게 없다. `files/`를 없앤 뒤의 디렉터리에는 DB 하나뿐이라
심링크 표면이 이미 거의 없고, 10절의 완화책(`Lstat` 미추적 순회, 플랫폼이 정하는 스냅샷
경로)은 어느 쪽을 택하든 필요하다.

### 왜 런타임에 플랫폼이 대신 만들어 줄 수 없는가

"생성과 삭제를 플랫폼이 기억하면 되지 않나"가 자연스러운 다음 질문인데, **플랫폼에는
그 순간에 끼어들 훅이 없다.** `-wal` 생성은 앱 프로세스 안에서 SQLite가 `open()`을
부르는 그 시점에 일어난다. Gitea가 inotify로 알아챘을 때는 이미 `EACCES`로 실패한
뒤다. 바인드 마운트가 되는 이유는 정확히 그 반대다 — 커널이 계속 강제하고, 매 순간
반응해야 하는 유저스페이스 참여자가 없다.

### 앱이 보는 위치는 항상 같다

앱 코드가 물리 경로를 알 필요는 없다. 샌드박스 모드별로 플랫폼이 경로를 맞춰 주고,
앱은 환경변수만 읽는다. `SOCKET`이 이미 같은 방식이다 (`appSocketForProcess`).

| 샌드박스 | `DATA_DIR` | 근거 |
|---|---|---|
| bubblewrap | `/data` | `--bind <물리경로> /data` — 앱은 문자 그대로 `/data`만 본다 |
| Landlock | 실제 경로 | 마운트 네임스페이스가 없어 경로를 바꿀 수 없다 |
| 없음(개발) | 실제 경로 | 동일 |

**앱 코드 계약: 경로를 literal로 쓰지 말고 `os.environ["DB_PATH"]`를 쓴다.**
`DATA_DIR`·`DB_PATH` 둘 다 `isReservedEnvName`에 넣어 앱이 덮어쓰지 못하게 한다
(`company/appproc.go:676`).

```python
import os, sqlite3
conn = sqlite3.connect(os.environ["DB_PATH"], timeout=10)
```

`DB_PATH`는 언제나 `${DATA_DIR}/app.db`다. 파일명을 플랫폼이 고정하는 이유는
마이그레이션 러너가 어느 파일을 열지 알아야 하기 때문이다.

### 해석 실패는 조용히 넘어가지 않는다

`AppDataDir(ctx, owner, repo)`는 `repo_model.GetRepositoryByOwnerAndName`으로 ID를
찾는다. 리포를 찾지 못하면 **빈 DB를 새로 만들지 않고 오류를 돌려준다.** 조용히 새 DB를
만드는 것은 사용자에게 데이터 유실과 구별되지 않는다.

**캐시하지 않는다.** owner/repo로 키를 잡은 캐시는 이름이 바뀌는 순간 낡고, 뒤에 다른
리포가 그 이름을 가져가면 낡은 항목이 **남의 데이터베이스를 건네준다.** 인덱스 한 번
타는 조회이고 배포·앱 시작에서만 일어나므로, 아낄 이유보다 틀릴 이유가 크다.

## 3. 삭제 — soft와 hard, 두 단계

앱을 지우는 것은 두 단계여야 한다. 지금은 한 단계뿐이고, 그 한 단계가 되돌릴 수 없다.

### Soft delete — `RemoveApp`이 하는 일

프로세스를 세우고, 라우트를 회수하고, 릴리스·venv를 지운다. 전부 재생성 가능한
것들이다. **데이터는 그대로 두고** `.meta.json`에 `removed_at`만 적는다.

기존 주석은 되돌릴 수 없음을 "코드는 git에 남는다"로 정당화한다
(`company/app_control.go:114`). 코드에는 맞고 데이터에는 틀린 말이다. 그래서 삭제의
의미를 둘로 나눈다.

### 복구 — 다시 배포하면 끝

보관 기간 안에는 **그냥 다시 배포하면 데이터가 그대로 돌아온다.** 별도의 복구 기능을
만들지 않는다. 2절에서 물리 위치를 리포 ID로 키잉했기 때문에 따라오는 성질이다.

### Hard delete — 영구 삭제

둘 중 하나로 일어난다.

- `APP_DATA_RETENTION_DAYS`(기본 90) 경과 후 GC가 쓸어간다
- 관리자가 "지금 영구 삭제"를 누른다 — 확인 + 사유 + 감사 기록

되돌릴 수 없고, 되돌릴 수 없다고 화면에 쓴다.

### 같은 시계를 쓰는 것들

- soft delete된 앱의 데이터
- 리포가 Gitea에서 삭제되어 고아가 된 데이터 (리포 ID로 더 이상 해석되지 않는다)
- 스냅샷 — 개수 상한 `APP_DATA_SNAPSHOT_KEEP`과 함께, 둘 중 먼저 걸리는 쪽

관리자 화면의 "보관 중인 데이터" 목록에 남은 일수, 용량, 마지막으로 본 owner/repo를
띄운다. 리포가 사라진 뒤에도 사람이 읽을 이름이 필요해서 `.meta.json`이 그것을 들고
있다.

## 4. 용량 — 상한, 그리고 양쪽 모두에게 보이는 상태

### 왜 측정만 하는가

앱 안에서 쓰기를 막을 방법이 없다. `PRAGMA max_page_count`는 커넥션 수명 동안만 유효해
파일에 영속되지 않고, 디스크 쿼터는 root가 필요한데 이 플랫폼에는 root가 없다
(`company/releasegc.go` 주석이 같은 이유로 GC를 두고 있다). 그래서 **측정 + 단계적
대응**이 유일하게 정직한 설계다.

측정은 60초 주기 디렉터리 순회다. `sampleAllApps`의 5초 주기와 분리한다 — 순회는
그보다 비싸고, 용량은 그렇게 빨리 변하지 않는다.

### 단계

| 조건 | 동작 | 앱 |
|---|---|---|
| `< APP_DATA_WARN_PCT` (기본 80%) | 없음 | 서비스 |
| `≥ WARN_PCT` | 부서 앱 화면 + 관리자 대시보드에 경고, 상태에 기록 | 서비스 |
| `≥ 100%` (`APP_DATA_QUOTA_MB`) | 새 배포 거부 — 스냅샷 여유가 없다. 경고 격상 | **계속 서비스** |
| 볼륨 여유 `< APP_DATA_HOST_FLOOR_MB` | 해당 앱 정지 (`ReasonDataFull`) | 정지 |

100%에서 앱을 세우지 않는 이유: DB가 가득 차도 읽기는 된다. 세우면 오히려 더 고장난
상태가 된다. 반면 볼륨 여유가 바닥나는 것은 `gitea.db`가 같은 볼륨에 있으므로 호스트
전체의 문제이고, 메모리 watchdog이 앱을 세우는 것과 같은 근거로 세운다.

### 보이는 곳

부서와 관리자가 **같은 사실을** 다른 말로 본다 — `usererror.go`의 기존 원칙 그대로.

- 부서: 앱 페이지에 사용량 막대와 "데이터 공간이 거의 찼습니다. 관리자에게 알려 주세요."
- 관리자: 대시보드 목록에 앱별 사용량/상한/비율, 정렬 가능. 경고 상태 앱은 상단 고정.

## 5. 이기종 환경 적응

리눅스 + bubblewrap이 기본이지만, 그것을 **가정하지 않는다.** 플랫폼은 이미 추측하지
않고 탐지한다 — `sandboxProbe`·`landlockProbe`·`pythonProbe`·`prlimitProbe`가 전부
`sync.OnceValues`로 한 번 확인하고 결과를 들고 다닌다. 데이터 계층도 같은 방식을 쓴다.
새 개념을 만들지 않는다.

### `dataProbe` — 물어보지 말고 해 본다

기동 시 1회, `AppDataPath` 아래에 임시 DB를 만들어 **실제로 시도한다.**

핵심은 `PRAGMA journal_mode=WAL`이 요청이 아니라 **결과를 돌려준다**는 점이다.
파일시스템이 WAL을 지원하지 않으면 SQLite는 조용히 이전 모드를 반환한다. 그래서
"여기가 NFS인가"를 마운트 정보로 추정할 필요가 없다 — 돌려받은 문자열을 읽으면 끝난다.
추정은 틀릴 수 있고, 이것은 틀리지 않는다.

결과는 `PlatformEnvironment`에 실어 관리자 화면과 AI 컨텍스트 양쪽에 노출한다
(`company/platformenv.go`). 파이썬 버전과 샌드박스 모드가 이미 그 길로 간다.

### 능력별 저하

| 탐지 대상 | 가능할 때 | 불가능할 때 |
|---|---|---|
| 샌드박스 모드 | `DATA_DIR` = `/data` (bwrap 바인드) | 실제 경로(Landlock·없음). 앱은 어차피 env만 읽으므로 코드는 그대로 |
| WAL | `journal_mode=WAL` | `TRUNCATE`로 강등하고 경고를 남긴다. 단일 프로세스라 동시성 손해가 작다 |
| 여유 공간 조회 | 호스트 바닥선 검사 | 검사를 건너뛴다. `applimits_linux.go`/`applimits_other.go`와 같은 빌드 태그 분리 |
| 스냅샷 | `Connection.backup()` | 조건 없음 — 파이썬 3.7부터 표준이다 |

여유 공간 조회가 안 되는 호스트에서 검사를 건너뛰는 것은 fail-open이다. 그래도 맞는
이유는, 샌드박스가 없는 호스트에서 이 플랫폼이 이미 운영 기동을 거부하기
때문이다(`allowUnsandboxed`). 그 경로에 남는 것은 개발 기계뿐이다.

### 스냅샷은 `VACUUM INTO`가 아니라 `backup()`

`VACUUM INTO`는 SQLite 3.27+를 요구하는데, 호스트의 libsqlite3 버전은 통제 밖이다.
`sqlite3.Connection.backup()`은 파이썬 3.7부터 표준이고 열린 DB에서도 정합적인 사본을
만든다. **버전 조건이 없는 쪽이 이기종에서 이긴다.**

스냅샷 디렉터리를 앱 데이터 디렉터리 *안에* 두는 이유도 여기 있다. 같은 파일시스템이어야
`os.Rename`이 원자적이다.

실측으로 확인한 것(SQLite 3.51.2): 초당 수천 건이 커밋되는 라이브 WAL DB에서 백업을
떠도 결과는 `integrity_check` 통과, **미커밋 트랜잭션은 포함되지 않는** 정합적 시점이며,
`-wal` 없이 **혼자 서는 파일 하나**가 나온다. 파일 하나라는 점이 호스트 밖 백업과 복원을
둘 다 단순하게 만든다.

`backup()`은 반드시 기본값(`pages=-1`, 한 번에 복사)으로 부른다. 페이지를 쪼개 쉬어 가며
복사하면, 그 사이에 원본이 쓰일 때 SQLite가 백업을 처음부터 다시 시작한다 — 쓰기가 잦은
앱에서는 끝나지 않을 수 있다.

### 탐지가 틀렸을 때

`APP_DATA_JOURNAL_MODE`로 덮어쓴다 — `auto`(기본)·`wal`·`truncate`. 자동 탐지를 믿되,
운영자가 반증할 수 있어야 한다.

## 6. 마이그레이션

### 형식

`app/migrations/NNN_name.sql` — 3자리 이상 0채움, 오름차순. 플랫폼이 적용하고
`_schema_migrations`에 기록한다.

```sql
CREATE TABLE IF NOT EXISTS _schema_migrations (
  version     INTEGER PRIMARY KEY,
  name        TEXT    NOT NULL,
  checksum    TEXT    NOT NULL,
  applied_at  INTEGER NOT NULL,
  sha         TEXT    NOT NULL,
  destructive INTEGER NOT NULL DEFAULT 0
);
```

### 실행

- 배포 중, **옛 앱을 멈추기 전에** 돌린다. additive라 돌고 있는 옛 코드에 보이지 않고,
  실패하면 아무것도 건드리지 않은 상태로 배포만 실패한다. 심링크 교체가 마지막이라는
  기존 원칙(`company/deployworker.go:134`)과 같은 논리다.
- 러너는 플랫폼 소유의 Python 스크립트이고, **새 릴리스의 venv로 샌드박스 안에서** 돈다.
  Go 쪽에 SQLite 의존성을 추가하지 않는다.
- SQL 본문·버전·체크섬을 Go가 읽어 stdin으로 JSON 페이로드를 넘긴다. 러너가 `/app`을
  읽지 않으므로 검증과 적용 사이의 TOCTOU가 없다.
- 마이그레이션 하나와 그 기록 행이 **한 트랜잭션**이다. SQLite는 DDL이 트랜잭션에
  포함되므로 중간에 죽어도 반쯤 적용된 상태가 남지 않는다.
- `PRAGMA journal_mode=WAL`은 트랜잭션 밖에서, DB 생성 시 1회. 파일에 영속된다.
- `ALTER TABLE` 12단계 재구축은 `PRAGMA foreign_keys=OFF`를 트랜잭션 밖에서 요구한다.
  러너는 전체를 하나의 `BEGIN`으로 감싸지 않는다.
- 타임아웃을 둔다(`APP_DATA_MIGRATE_TIMEOUT`). 폭주한 마이그레이션이 배포를 영원히
  붙들면 안 된다.

### 규칙 — additive only

DROP TABLE / DROP COLUMN / RENAME / DEFAULT 없는 NOT NULL은 **기계적으로 거부**한다.
`-- platform: destructive` 표식이 있는 파일만 예외이고, 그것은 Deploy Request에서
관리자 승인을 거친다.

이유는 7절에 있다. 무제한 과거 배포가 가능한 이 플랫폼에서, additive only는 롤백
호환성을 **무한히** 보장하는 유일한 규칙이다.

### 체크섬

이미 적용된 버전의 파일 내용이 바뀌면 배포를 거부한다. "버전이 올라가도 흔들리지 않는다"를
보장하는 것이 이 한 줄이다.

### 앱이 직접 만든 테이블

`/data`가 앱에게 쓰기 가능해야 하는 이상, 런타임 `CREATE TABLE`을 막을 방법은 없다.
그래서 막지 않고 **감지해서 편입한다.**

- 매 실행 후 `sqlite_master`를 정규화해 해시한 **스키마 지문**과 `PRAGMA schema_version`을
  기록한다.
- 다음 배포에서 지문이 다르면 앱이 밖에서 스키마를 바꾼 것이다.
  - **추가만 있으면**: `sqlite_master`의 DDL 텍스트로 `NNN_adopt_*.sql`(전부
    `IF NOT EXISTS`)을 생성해 체인에 편입하고 배포 로그에 남긴다. 런타임에 생긴 테이블은
    옛 코드에 애초에 보이지 않으므로 additive 규칙을 자동으로 만족한다.
  - **사라진 것이 있으면**: 편입하지 않는다. 관리자에게 경고를 올린다. 자동 복구를
    시도하는 것이 스냅샷 복원보다 나은 경우가 없다.

## 7. 롤백 — 제한을 두고, 나머지는 사람이 한다

### 거리가 무제한이라는 사실

`DeployVersion`은 git 히스토리의 **임의 커밋**을 소스에서 다시 빌드해 배포한다
(`company/deployversion.go:29`). `releasesKept = 5`는 디스크만 제한할 뿐 이것을 막지
않는다. 1년 전 코드가 오늘의 스키마를 만날 수 있다.

### 기계적 바닥선

배포 시 계산한다.

```
applied = _schema_migrations 의 버전 집합
present = 이 릴리스의 app/migrations/ 버전 집합
pending = present - applied     → 순서대로 적용
missing = applied - present     → 이 릴리스가 DB보다 과거
```

`missing`이 전부 additive면 **허용한다** — 옛 코드는 여분의 컬럼·테이블을 그냥 보지
않는다. 하나라도 destructive면 **이유를 밝히고 거부한다.**

### 정책적 거리 제한

DB가 존재하는 앱에 한해, 부서는 `APP_DATA_ROLLBACK_MAX_DAYS`(기본 30)보다 오래된
버전을 배포할 수 없다. 그 너머는 관리자만 가능하다. 자동으로 뚫지 않는다.

### 관리자 데이터 콘솔 — 수동 개입 경로

되돌리기가 데이터 변경을 요구하는 상황은 자동화할 수 없다. 관리자가 직접 본다.

| 기능 | 조건 |
|---|---|
| 스냅샷 만들기 / 목록 | 언제나 |
| 스냅샷 복원 | 앱 정지 필수. 복원 직전 현재 상태를 자동 스냅샷 |
| DB 내려받기 | 감사 기록 + 사유 입력 |
| 검토된 SQL 실행 | 앱 정지 필수. 직전 자동 스냅샷. 트랜잭션 + 영향 행 수 확인 후 커밋 |
| 바닥선·거리 제한 넘어 배포 | 명시적 확인 + 사유 입력 |

SQL 콘솔은 `APP_DATA_SQL_CONSOLE`로 **기본 비활성**이고, 부서에는 어떤 경로로도
노출되지 않는다.

## 8. 데이터 반출과 외부 이관

가두는 플랫폼은 신뢰받지 못한다. 데이터를 꺼내는 길이 처음부터 있어야 한다.

### 반출 번들

관리자가 버튼 하나로 zip 하나를 받는다.

| 파일 | 무엇 | 왜 |
|---|---|---|
| `app.db` | 검증된 스냅샷 | 손실 없는 원본. 어떤 SQLite 도구로도 열린다 |
| `dump.sql` | `iterdump()` 출력 | 다른 SQLite로 그대로 들어간다 |
| `tables/<name>.csv` | 테이블별 CSV | 엔진을 가리지 않는 보편 경로 |
| `migrations/NNN_*.sql` | 적용된 마이그레이션 전부 | 스키마의 역사가 평문 SQL로 남는다 |
| `manifest.json` | 아래 참조 | 받은 쪽이 무엇을 받았는지 확인할 수 있다 |

`manifest.json`에는 owner/repo와 리포 ID, 스냅샷 시각, 적용된 마이그레이션과 체크섬,
테이블별 행 수, `integrity_check` 결과, 스키마 지문이 들어간다. 번들이 스스로를 설명하고
**검증 가능**해야 이관이 "복사했다"에서 끝나지 않는다.

### 만드는 위치는 샌드박스 안이다

여기에 조용한 경계 위반이 숨어 있다. DB 파일의 **내용은 부서 앱이 쓴 것**이다. 그것을
Gitea 자신의 프로세스에서 파싱하면, 샌드박스로 막아 둔 신뢰 경계를 반출 기능이 뒷문으로
넘는 셈이 된다. 그래서 나눈다.

- `app.db` 복사는 **바이트 복사**다. 파싱이 없으므로 플랫폼이 직접 한다
- `dump.sql`·CSV·행 수·`integrity_check`는 **샌드박스 안에서** 앱의 파이썬으로 만든다.
  마이그레이션 러너와 같은 경로를 쓰고, 임시 `/export` 바인드에 쓴 뒤 스트리밍하고 지운다
- `manifest.json`은 플랫폼이 아는 부분(리포 ID·마이그레이션·시각)과 러너가 아는
  부분(행 수·지문)을 합쳐 플랫폼이 쓴다

`/export`는 임시이고 용량 상한에 포함되지 않는다. 반출 때문에 앱이 상한에 걸리면 안 된다.

### 다른 엔진으로 옮길 때

정직하게: PostgreSQL·MySQL로 가는 **자동 변환기는 만들지 않는다.** 타입 친화성,
`AUTOINCREMENT`, `WITHOUT ROWID`, 표현식 기본값은 기계적으로 옮겨지지 않고, 반쯤 맞는
변환기는 없는 것보다 나쁘다.

대신 옮기기 쉬운 재료를 준다. CSV는 어느 엔진에나 들어가고, `migrations/`는 ORM 없는
평문 SQL이라 사람이 읽고 목적지 문법으로 고칠 수 있다. 6절의 additive-only·평문 SQL
규칙이 여기서 두 번째 값을 한다 — 스키마의 역사가 처음부터 이식 가능한 형태로 남는다.

목적지가 타입을 엄격히 따지는 엔진이면 `STRICT` 테이블이 변환량을 크게 줄인다.
`dataProbe`가 잰 SQLite가 3.37 이상일 때 AI 계약에서 **권장**한다. 요구가 아닌 이유는
5절과 같다 — 버전 조건을 필수로 만들면 이기종에서 진다.

### 권한과 감사

- 관리자 전용. 부서 경로는 없다
- 매 반출에 실행자·시각·앱·사유를 기록한다. 개인정보가 들어 있을 수 있는 파일이 기계
  밖으로 나가는 동작이고, 그 사실이 나중에 확인 가능해야 한다
- 응답은 `no-store`. 번들은 웹에서 접근 가능한 경로에 쓰지 않고 스트리밍한다
- 반출은 **스냅샷에서** 뜬다. 라이브 DB를 직접 읽지 않는다 — 5절에서 잰 대로 스냅샷이
  정합적이므로 라이브를 잠글 이유가 없다

정책은 바뀐다. 부서 반출은 설정으로 열 수 있게 둔다(`APP_DATA_EXPORT_DEPARTMENT`,
기본 `false`).

## 9. 설정

정책은 바뀐다. 상수로 박지 않고 전부 `app.ini`의 `[company]`에서 읽는다.
`companySetting`은 `setting.CfgProvider`를 호출 시점에 읽으므로
(`company/appsandbox.go:253`) 대부분의 값은 재시작 없이 반영된다.

| 키 | 기본 | 뜻 |
|---|---|---|

| `APP_DATA_QUOTA_MB` | `128` | 앱당 상한 |
| `APP_DATA_WARN_PCT` | `80` | 경고 시작 비율 |
| `APP_DATA_HOST_FLOOR_MB` | `1024` | 볼륨 여유 하한 — 밑돌면 앱 정지 |
| `APP_DATA_RETENTION_DAYS` | `90` | 삭제·고아 데이터, 스냅샷 보관 기간 |
| `APP_DATA_SNAPSHOT_KEEP` | `10` | 앱당 스냅샷 개수 상한 |
| `APP_DATA_SNAPSHOT_DAILY` | `true` | 배포 시점 외에 하루 1회 스냅샷 |

| `APP_DATA_EXPORT_DEPARTMENT` | `false` | 부서도 자기 앱 데이터를 반출 가능 |

앱별 상한은 관리자 소유 `apps.yml`의 `limits.dataMB`로 덮어쓴다.

## 10. 보안 검토

### 이 기능이 새로 여는 표면

1. **심링크 탈출.** 앱은 Gitea와 같은 UID로 돌고 `/data`에 쓸 수 있으므로, 데이터
   디렉터리 안에 바깥을 가리키는 심링크를 만들 수 있다. 앱 자신은 그것으로 탈출하지
   못한다(bwrap은 네임스페이스 안에서 해석하고, Landlock은 실제 경로에 규칙을 건다).
   위험한 쪽은 **플랫폼이다**: 용량 순회가 심링크를 따라가면 남의 디렉터리를 세고,
   스냅샷 대상이 조작되면 플랫폼 권한으로 바깥에 쓴다.
   → 순회는 `filepath.WalkDir` + `Lstat`로 심링크를 따라가지 않는다. 스냅샷 경로는
   항상 플랫폼이 생성하고, 사용자 입력이 파일명에 닿지 않는다.
2. **경로 주입.** 디렉터리 키는 DB에서 온 int64이고 문자열이 아니다. 릴리스 경로가
   SHA를 해싱해 쓰는 것(`releaseDir`)과 같은 이유다.
3. **에러 누출.** SQLite 오류 메시지는 절대 경로를 담는다. 부서 화면에 닿기 전에
   `RedactServerPaths`를 통과시킨다 (`company/usererror.go` 선례).
4. **SQL 콘솔.** 기본 비활성, 관리자 전용, 앱 정지 필수, 직전 자동 스냅샷, 트랜잭션
   커밋 전 영향 행 수 확인, 문장 길이 상한과 타임아웃, 실행자 기록. 부서 경로 없음.
5. **DB 내려받기.** 개인정보가 들어 있을 수 있다. 관리자 전용, 감사 기록,
   `no-store`.
6. **러너 권한.** 마이그레이션 러너는 앱과 **같은** 샌드박스·같은 한도로 돈다. `/data`
   외에 추가 바인드를 주지 않는다. 실행하는 SQL은 부서가 통제하는 릴리스에서 왔지만,
   닿을 수 있는 범위가 그 앱 자신의 DB 파일 하나뿐이라는 것이 격리 경계다.
7. **동시 쓰기.** 기본 start 명령이 단일 프로세스라는 점이 SQLite를 안전하게 만든다
   (`company/appconfig.go:149`). 데이터 기능이 켜진 앱에서 `--workers`가 1보다 크면
   배포를 거부한다.

### 운영자가 확인해야 하는 것

없다. WAL 가능 여부를 포함한 환경 차이는 5절의 `dataProbe`가 기동 시 자동으로 판정하고
결과를 관리자 화면에 남긴다. 운영자가 읽어야 할 문서 한 줄보다, 플랫폼이 스스로 재는
쪽이 언제나 맞다.

## 11. 안전 운영의 조건

이 문서의 설계가 닫는 것은 **플랫폼 자신의 동작으로 데이터가 사라지는 경로**다 — 배포,
롤백, 이름 변경, 앱 삭제. 애초에 고치려던 문제가 그것이다.

닫지 못하는 것이 남는다. 구현하면 안전해지는 것이 아니라, 아래가 함께 있어야 안전해진다.

### 호스트 밖 백업이 없으면 백업이 아니다

스냅샷은 DB와 **같은 디렉터리·같은 파일시스템·같은 기계**에 있다. `os.Rename`을
원자적으로 만들려고 그렇게 뒀고, 그 대가로 디스크가 죽거나 파일시스템이 깨지거나 누가
`AppDataPath`를 잘못 지우면 DB와 모든 스냅샷이 **함께** 사라진다.

스냅샷은 실수 복구용이지 재해 복구용이 아니다. 호스트 밖으로 나가는 사본이 따로 있어야
한다. root도 없고 외부 네트워크도 기본 차단인 이 플랫폼에서 현실적인 형태는, 이미 도는
Gitea 백업 경로에 `company-app-data/`를 포함시키는 것이다. **그것이 없으면 이 기능을
켜지 않는다.** 이건 권고가 아니라 전제 조건이다.

### 복원해 본 적 없는 복원 경로는 없는 것과 같다

스냅샷을 만드는 코드는 조용히 썩지 않지만 복원 코드는 썩는다. 만든 직후 자동으로
검증한다 — 열어서 `PRAGMA integrity_check`, 스키마 지문 대조, 행 수 기록. 검증에
실패한 스냅샷은 스냅샷으로 세지 않고, 관리자 화면에 검증 시각을 함께 띄운다.

### 앱의 논리 버그는 스냅샷 시점까지만 되돌아간다

앱이 `DELETE FROM ...`을 잘못 실행하는 것은 막을 수 없다(6절). 복원 단위가 "스냅샷
시점의 DB 전체"이므로 그 이후의 정상적인 변경도 함께 사라진다. 시점 복구(PITR)는 이
설계에 없고, 넣지 않는다 — 부서 앱 규모에서 그 복잡도는 정당화되지 않는다. 대신
스냅샷을 배포 시점뿐 아니라 일 단위로도 찍어 손실 창을 좁힌다(`APP_DATA_SNAPSHOT_DAILY`).

### 그 밖에 남는 것

- **고아 프로세스.** Gitea가 강제 종료되면 앱이 살아남는다(`company/appproc.go`의 기존
  문제). WAL은 다중 프로세스 쓰기를 견디므로 파일이 깨지지는 않지만, 옛 프로세스와 새
  프로세스가 같은 DB에 각자 쓰는 구간이 생길 수 있다. 소켓 점검(`socketInUse`)이 1차
  방어인데, DB가 생긴 뒤에는 그것만으로 충분하지 않다.
- **용량은 사후 측정이다.** 60초 표본 사이에 상한을 넘길 수 있다. 호스트 바닥선이 실질
  방어선이고 그것도 표본이다.
- **마이그레이션이 라이브 앱의 쓰기를 막는다.** 심링크 교체 전에 돌리기로 한 선택의
  대가다. 큰 테이블에서는 `busy_timeout` 안에 끝나지 않아 사용자에게 오류가 보일 수 있다.
- **동시성은 결국 앱 코드에 달려 있다.** 단일 프로세스가 전제를 만들어 주지만, FastAPI의
  동기 엔드포인트는 스레드풀에서 돌기 때문에 커넥션을 공유하면 깨진다. 요청마다 커넥션을
  열고 `busy_timeout`을 거는 것이 계약이고, 이건 플랫폼이 아니라 Phase 5(AI 계약)가
  지킨다.

## 12. 실패 모드

| 상황 | 결과 |
|---|---|
| 마이그레이션 실패 | 배포 실패. 심링크 교체 전이라 옛 버전이 그대로 서비스 |
| 체크섬 불일치 | 배포 거부. 어느 버전이 바뀌었는지 명시 |
| destructive가 `missing`에 있음 | 배포 거부. 관리자 강행 경로 안내 |
| 용량 100% | 배포 거부, 경고. 앱은 서비스 유지 |
| 볼륨 여유 바닥 | 앱 정지, `ReasonDataFull` |
| 리포 이름 변경 | 데이터 그대로. 릴리스·환경변수는 기존대로 재키잉됨 |
| 리포 삭제 | 데이터 보관, 90일 시계 시작 |
| 앱 삭제(soft) | 데이터 보관, 90일 시계 시작. 재배포하면 그대로 복구 |
| 영구 삭제(hard) | 되돌릴 수 없음. 확인·사유·감사 기록을 요구 |
| WAL 불가 파일시스템 | `TRUNCATE`로 자동 강등, 경고 기록. 배포는 계속된다 |
| 여유 공간 조회 불가 | 바닥선 검사 생략. 샌드박스 없는 운영 기동은 이미 거부된다 |
| Gitea가 마이그레이션 중 죽음 | 트랜잭션 롤백. 다음 배포가 같은 지점부터 |
| 지문 불일치(추가만) | 자동 편입 + 로그 |
| 지문 불일치(삭제 포함) | 편입 안 함. 관리자 경고 |
| 파괴적 런타임 DDL | **막을 수 없음.** 스냅샷 복원이 유일한 대응 |
| 디스크·파일시스템 손상 | DB와 스냅샷이 함께 사라진다. 호스트 밖 백업만이 답 (11절) |
| 스냅샷 검증 실패 | 스냅샷으로 세지 않고 관리자에게 알린다 |

## 13. 구현 순서

**Phase 0 — 데이터를 켜기 전에 반드시** (이것 없이 시작하면 소실 경로가 열린다)

- [x] **전제 조건 확인**: `AppDataPath`가 호스트 밖 백업 경로에 포함되는가 (운영자 확인함)
- [x] `company-app-data/<repoID>` 트리와 `AppDataDir` 해석기 (`company/appdata.go`)
- [x] `RemoveApp`을 soft delete로 — 데이터 보존, `.meta.json`의 `removedAt`
- [x] hard delete 스윕 (`APP_DATA_RETENTION_DAYS`) + 고아 감지
- [x] `PurgeAppData`·`ListAppDataArchives` — 관리자 화면 연결은 Phase 4

**Phase 1 — 앱이 쓸 수 있게** (`company/appdata.go`, `appsandbox.go`, `appproc.go`)

- [x] `appDataDirForProcess` + bwrap `--bind`, Landlock `--rw`
- [x] `DATA_DIR`·`DB_PATH` 주입 및 예약어 등록
- [x] `dataProbe` — WAL 실측, `TRUNCATE` 강등, `PlatformEnvironment` 노출

**Phase 2 — 용량**

- [x] 60초 순회 측정(심링크 미추적) + 메모리 캐시
- [x] 부서 화면 사용량 막대, 관리자 앱 화면 KPI
- [x] `/company-deploys` 목록에 앱별 사용량 열
- [x] 단계별 대응과 `ReasonDataFull`, 100%에서 배포 거부

**Phase 3 — 마이그레이션** (`company/appmigrate.go`)

- [x] 러너(Python, `run/migrate.json` 페이로드) + `_schema_migrations`
- [x] DDL 가드와 체크섬
- [x] 스냅샷(`Connection.backup()`) 및 개수·기간 양쪽 보관 한도
- [x] 스냅샷 자동 검증 (`integrity_check`)
- [x] `pending`/`missing` 계산과 바닥선 거부
- [x] 지문 기반 드리프트 감지 (`_schema_state`)

**Phase 4 — 사람의 개입** (`company/appdatatool.go`, `admin_app_data.go`)

- [x] 관리자 데이터 콘솔 (스냅샷·복원, 보관 데이터 즉시 영구 삭제)
- [x] 반출 번들 (zip + `manifest.json`, 파싱은 샌드박스 안에서)
- [x] SQL 콘솔 (기본 비활성, 앱 정지 필수, 직전 자동 스냅샷)
- [x] 거리 제한(`APP_DATA_ROLLBACK_MAX_DAYS`)과 관리자 강행 경로

**Phase 5 — AI 계약**

- [x] `PlatformEnvironment.AIContext()`에 규칙 추가: 앱 코드에서 DDL 금지,
      `os.environ["DB_PATH"]` 사용, 스키마 변경은 새 마이그레이션 파일, additive only,
      요청당 커넥션, 업로드는 BLOB

**구현하면서 문서와 달라진 것**

- 해석기에 **캐시를 두지 않았다.** owner/repo 키 캐시는 이름 변경 뒤 낡고, 다른 리포가
  그 이름을 가져가면 남의 데이터베이스를 건네준다(2절).
- 드리프트 편입은 마이그레이션 **파일을 만들지 않는다.** 릴리스 트리는 읽기 전용이고
  파일 생성은 부서 리포에 커밋하는 일이 된다. 대신 `_schema_state`에 지문을 기록해
  추가·삭제를 배포 로그와 관리자 경고로 보고한다.
- SQL 콘솔은 미리보기/커밋 2단계를 두지 않았다. 앱 정지 + 직전 자동 스냅샷이 되돌릴
  방법을 보장하므로, 단계를 늘리는 쪽이 얻는 것보다 복잡하다.

Phase 5는 마지막이 아니라 가장 높은 지렛대일 수 있다. 부서 앱 코드는 어시스턴트가
쓴다. 계약을 모델에게 알려주지 않으면 생성되는 앱마다 지금의 버그를 반복한다.
