# 앱 배포 플랫폼 — 아키텍처와 보안 모델

부서가 올린 FastAPI/Flask 앱을 이 Gitea 인스턴스가 직접 빌드·실행·감시·제어하는 구조.
구현 방법은 [app-platform-impl.md](app-platform-impl.md), 진행 상황은 [app-platform-tasks.md](app-platform-tasks.md).

## 왜 만드는가

현재 Deploy Request 흐름은 **관리자가 merge하는 순간 끝난다.** 스냅샷 커밋이 central-deploy에 올라가고 브랜치가 삭제되면 파이프라인이 종료된다. [architecture.md](architecture.md)가 서술하는 push mirror는 **문서상 의도일 뿐 미구현**이다(DB에 push mirror 0건, webhook 0건, `.gitea/workflows` 0개).

목표는 **"Gitea에 올리면 실행 중인 상태에서 바로 동작"** 하고, 관리자가 운영 중인 앱을 한 화면에서 모니터링·제어하는 것까지 하나의 플랫폼에서 끝내는 것이다.

## 결정적 제약

**배포 서버에 root가 없다.** `sudo`는 apt 등 일부만 허용되고 `journalctl`도 막혀 있다. 따라서 systemd 유닛 설치·`useradd`·sudoers·`/etc/nginx` 작성·journald가 **전부 불가능**하다. 이 설계는 root를 한 번도 요구하지 않는다.

## 구조

```
직원 편집 → Deploy Request → 관리자 merge
                                  ↓
              central-deploy 기본 브랜치에 스냅샷 커밋
                                  ↓
        Gitea가 .company/apps.yml 을 읽고 직접 실행 (act_runner 없음)
                                  ↓
     venv 빌드 → 릴리스 디렉터리 → current 심볼릭 링크 원자적 교체
                                  ↓
        bubblewrap 샌드박스로 앱 기동 (Gitea의 자식 프로세스)
                                  ↓
              헬스체크 → 실패 시 이전 릴리스로 자동 롤백
                                  ↓
   Gitea가 리버스 프록시로 /apps/{org}/{repo}/ 서빙 + 지표·로그 수집
```

systemd가 하던 일(프로세스 소유·수명 관리)과 nginx가 하던 일(리버스 프록시)을 **Gitea가 직접** 한다. root가 없어서 내린 결정이지만, 부수적으로 지표·로그·제어가 전부 인프로세스로 해결된다.

## 핵심 결정과 근거

| 결정 | 근거 |
|---|---|
| **Docker 미사용** | 컨테이너는 커널을 공유해 강한 경계가 아니고, runner가 Docker 소켓에 접근해야 하는데 **그건 제약 없는 root와 동등**하다. 레지스트리·이미지 운영 부담도 는다 |
| **bubblewrap 샌드박스** | root 없이 마운트·PID·네트워크 네임스페이스를 얻는다. Landlock은 **네트워크를 못 막고**(ABI v4는 커널 6.7+) 같은 UID의 `/proc` 관찰도 남아 부족했다 |
| **act_runner 미사용** | 파이썬은 컴파일이 없어 "빌드"가 `pip install` 한 줄이다. 명령 하나를 위해 별도 에이전트·워크플로 문법·토큰을 도입할 이유가 없다 |
| **DB 마이그레이션 금지** | `modelmigration/migrations.go`는 순차 번호 append-only 목록이라(현재 330번) fork가 331을 추가하면 업스트림과 **텍스트로도 의미로도 충돌**한다. 플랫 JSON을 쓴다 |
| **Gitea가 리버스 프록시** | nginx 설정에 접근할 수 없다. 부수 이득으로 모든 요청이 Gitea를 지나 **지표가 로그 파싱 없이** 나오고, 인증·다운로드 정책을 강제할 수 있다 |
| **`[actions] ENABLED = false`** | 직원이 자기 저장소 루트에 `.gitea/workflows/`를 넣을 수 있다. 지금 안 도는 유일한 이유가 "runner가 0개"라 통제가 아니다 |

## 보안 모델

### 위협

**비개발자가 임의의 파이썬 코드를 올리고, 관리자 merge 후 서버에서 실행된다.** root가 없어 부서별 OS 계정을 만들 수 없으므로 **앱은 Gitea와 같은 계정으로 돈다.**

### 샌드박스가 없을 때 탈취 가능한 것 (실측)

| 대상 | 결과 |
|---|---|
| `data/sessions/` (`PROVIDER = file`) | **활성 세션 탈취 → 관리자로 즉시 로그인.** 비밀번호 불필요 |
| `data/gitea.db` | 전 사용자 계정·이메일·비밀번호 해시·토큰 |
| `data/gitea-repositories/` | **모든 부서의 모든 저장소 전문**(central-deploy 포함) |
| `custom/conf/app.ini` | `INTERNAL_TOKEN`, `JWT_SECRET`, `LFS_JWT_SECRET` |

세션 파일이 가장 위험하다 — 정보 탈취를 넘어 **즉시 관리자 권한 획득**이다.

### 샌드박스가 막는 것 / 안 막는 것

`network.mode: none` 기준.

| 시도 | 차단 | 근거 |
|---|---|---|
| `requests.get/post()`, 소켓 연결 | ✅ | netns에 외부 경로 없음. DNS부터 실패 |
| `ping` | ✅ | 경로 없음 + `CapabilityBoundingSet=` 비움 |
| `curl`/`wget` 실행 | ✅ | 실행되나 네트워크가 없어 실패 |
| `subprocess`/`exec` | ❌ 실행됨 | **자식이 샌드박스를 상속**하므로 도달 범위는 0 |
| 타 부서 코드·`app.ini`·DB 읽기 | ✅ | 마운트 네임스페이스에 존재하지 않음 |
| 타 프로세스 관찰·시그널·ptrace | ✅ | PID 네임스페이스 |
| `rm -rf /` | ✅ | 읽기 전용 바인드는 `EROFS`, Gitea 데이터는 애초에 없음. **자해로 끝난다** |

`execve`를 seccomp으로 막지 않는다 — 자식이 같은 감옥에 갇히므로 이득이 거의 없고 멀티프로세싱만 깨진다. **"무엇을 실행하든 나갈 곳이 없다"** 가 방어의 축이다.

**막지 못하는 것:** 디스크·메모리 고갈은 완전히는 못 막는다(쿼터는 root 필요). `rlimit`과 tmpfs 상한으로 줄이고 사용량을 관리자 화면에 노출한다.

### root 취득 시나리오

| 경로 | root | 실제 도달점 |
|---|---|---|
| 샌드박스 탈출 | ✗ | Gitea 계정 (sudo 없음) |
| `pip install` 악성 패키지 | ✗ | Gitea 계정으로 코드 실행 |
| Gitea 자체 취약점 | ✗ | Gitea 계정 |
| 관리자 계정 탈취 | ✗ | 플랫폼 통제권 (OS 아님) |
| **커널 취약점 (user namespace)** | ✅ | **유일한 실질 경로** |

**sudo를 쓰지 않으므로 Gitea 계정을 완전히 장악해도 root가 아니다.** 다만 **공격자의 실질적 목표는 root가 아니라 Gitea 계정**이다 — 그것만 잡으면 세션으로 관리자를 사칭하고 모든 저장소를 읽는다. **방어의 초점은 "root 차단"이 아니라 "Gitea 계정 보호"** 다.

**가장 현실적인 경로는 `pip`** 이다. 샌드박스 **밖에서** Gitea 계정으로 임의 코드가 실행된다. `--only-binary=:all:`은 설치 시점 실행만 막고, **진짜 통제는 허용 목록**이다 — 이것이 이 시스템의 **가장 중요한 단일 통제**다.

> **정직한 트레이드오프:** bubblewrap은 비특권 user namespace를 요구하는데 **그것 자체가 커널 공격면을 넓힌다.** 일부 배포판이 막아두는 이유이기도 하다. 완화책은 커널 패치 유지뿐이며, 서버 관리자와 공유해야 한다.

### 3겹 의존성 방어

1. **입력 검증** — `이름==버전`만 허용. `git+`·URL·`-e`·`--index-url` 거부
2. **허용 목록** — 관리자 승인 패키지만. 앱별 `allowed_extra`로 최소 권한
3. **샌드박스** — 설치돼도 나갈 곳이 없다

1·2가 "설치되지 않게" 막고, 3이 "설치돼도 소용없게" 만든다.

## 권한 경계

| 부서가 스스로 | 부서가 요청 → 관리자 승인 | 관리자 전용 |
|---|---|---|
| 앱 시작·중지·재시작·롤백 | 접근 권한 넓히기 (inbound) | 강제 정지·앱 제거 |
| 앱 이름·설명 | 외부 통신 대상 (outbound) | 배포 활성/비활성 |
| 환경변수 | 패키지 추가 | 기본 한도·기본 정책 |
| 접근 권한 좁히기 | 자원 한도 상향 · 파일 다운로드 허용 | |

**좁히는 건 즉시, 넓히는 건 승인.** 안전한 방향은 막을 이유가 없고, 노출을 늘리거나 공용 자원을 더 쓰는 것만 관리자가 본다.

**관리자는 플랫폼을 운영하는 것이지 부서 앱의 가동 여부를 판단할 위치가 아니다.** 다만 `stopped`(부서가 껐음, 부서가 켤 수 있음)와 `suspended`(관리자가 정지, 부서는 못 켬)를 **반드시 구분**해야 관리자의 보호 조치가 의미를 갖는다.

## 운영자는 개발자가 아니다

**일상 운영은 100% 화면에서 끝나야 한다.** 승인 버튼을 누르면 Gitea가 `apps.yml`을 대신 커밋하므로 YAML도 git도 몰라도 된다.

개발자가 필요한 것은 **최초 설치 1회**와 **업스트림 Gitea 업그레이드** 둘뿐이다.

이를 위한 원칙:
1. **운영 중 바뀔 값은 app.ini에 두지 않는다** — app.ini 수정은 재시작을 부르고 그건 셸 작업이다
2. **`apps.yml`과 앱 항목은 자동 생성한다** — 관리자가 미리 만들어둘 것이 없다
3. **실패 원인을 평문으로 보여준다** — 로그를 읽혀 원인을 찾게 하면 결국 개발자를 부른다

## 격리: 실제로 무엇을 쓰는가 (2026-09-06 갱신)

배포 서버에서 `unshare -Ur true`가 `write failed /proc/self/uid_map: Operation
not permitted`로 실패했다. **비특권 user namespace가 막혀 있어 bubblewrap을 쓸
수 없다.** Ubuntu 24.04의 기본 정책(`kernel.apparmor_restrict_unprivileged_userns`)
이며, 관리자가 별도로 강화한 것이 아니다 — 즉 꺼 달라고 요청하는 것은 배포판
기본 보안을 낮춰 달라는 요청이 된다.

그래서 격리를 3단으로 두고, 가능한 가장 강한 것을 고른다:

| 순위 | 방식 | 조건 | 비고 |
|---|---|---|---|
| 1 | **bubblewrap** | 비특권 userns 허용 | 가장 강함. 마운트·PID·네트워크 네임스페이스 |
| 2 | **Landlock + seccomp** | 커널 5.13+ (네트워크는 6.7+) | 현재 서버가 쓰는 경로. 커널 6.8 확인 |
| 3 | 무격리 | 관리자 명시 옵트인 | 기본 거부. 비Linux 개발 환경만 자동 허용 |

### Landlock 경로가 bubblewrap보다 약한 지점 (정직하게)

| | bubblewrap | Landlock + seccomp |
|---|---|---|
| Gitea 데이터 | 파일시스템에 **존재하지 않음** | 존재하지만 **접근 거부** |
| 타 프로세스 | PID 네임스페이스로 안 보임 | `/proc` 차단으로 안 보임 (`/proc/self`만 허용) |
| 프로세스 트리 정리 | PID 1 종료로 **전부 정리** | 프로세스 그룹에 의존 — 고아 가능성이 남는다 |
| 외부 TCP | netns에 경로 없음 | Landlock이 connect/bind 거부 |
| UDP·raw 소켓 | netns에 경로 없음 | **seccomp가 `socket()`을 주소 패밀리로 거부** |
| Gitea에 시그널 | PID 네임스페이스로 불가 | seccomp가 `kill(-1)`·`kill(giteaPID)` 거부 |
| `/tmp` | 앱별 tmpfs (크기 상한) | **호스트 공유이므로 아예 차단**, 앱별 `HOME`/`TMPDIR`로 대체 |

**남는 실질 차이는 프로세스 트리 정리 하나다.** 나머지는 "없앰"과 "막음"의 차이라
공격자 입장에서는 동일한 결과다.

### 왜 서브커맨드가 필요한가

Landlock과 seccomp는 **fork와 exec 사이, 자식에서** 걸어야 하고 Go의 `os/exec`에는
그 훅이 없다. 그래서 `gitea deptapp-exec`가 있다 — Gitea가 이것을 실행하면, 이것이
자기 자신을 잠근 뒤 앱을 `execve`한다. 두 제한 모두 `execve`를 건너 상속되므로 앱은
빠져나올 수 없는 상태로 시작한다. rlimit도 같은 지점에서 걸므로 `prlimit(1)`
의존성이 사라졌다.

### seccomp가 할 수 있는 것과 없는 것

seccomp는 **스칼라 인자만** 본다 — 포인터를 역참조하지 않는다. 그래서 소켓의
*주소 패밀리*는 거를 수 있지만 *목적지 주소*는 영원히 못 본다. 주소 단위 정책은
송신 브로커의 몫이며, 이 필터의 몫이 아니다.

필터는 **기본 허용**이다. 기본 거부가 더 강하지만 CPython과 임의의 wheel이 낼 수
있는 syscall을 전부 열거해야 하고, 그 목록이 틀리면 부서 앱이 아무도 진단할 수 없는
이유로 죽는다. 파일시스템과 네트워크는 Landlock이 기본 거부로 잡고 있으므로,
이 필터는 Landlock이 못 덮는 구멍만 정확히 막는다.

## 착수 전 서버 확인 (필수)

```bash
unshare -Ur true                                # 비특권 user namespace 허용 여부
apt-cache policy bubblewrap                     # 설치 가능 여부
pip download --no-deps --dest /tmp/x requests    # PyPI 접근 가능 여부
uname -r                                         # 커널 버전
```

첫 번째가 실패하면 **이 설계의 안전성 전제가 무너진다.** 그 경우 서버 관리자에게 **앱 전용 OS 계정 하나**를 요청하는 쪽으로 전환한다 — 계정이 분리되면 파일 권한만으로 대부분이 해결되며, 가장 높은 레버리지의 요청이다.

세 번째가 실패하면 사내 PyPI 미러가 필요하다. 미러가 있으면 위 공급망 위험도 함께 줄어든다.
